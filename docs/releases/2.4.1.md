# bazis-statusy 2.4.1

Requires bazis 2.4.2 and bazis-permit 2.4.1.

## Fixes

- **A project with a model with a status did not load without its database**: building
  the routes computed the default status with a query, so the system checks,
  `manage.py bazis_doctor`, `bazis_introspect` and `makemigrations` failed until the
  database was created. Now the default status comes from `BS_BAZIS_STATUS_INITIAL` when
  the database cannot be connected to.
- **`makemigrations` of a project wrote a migration into the installed package** when the
  languages of the project were not English and Russian (the default is English only): the
  translated fields `name` of `Status` and `Transit` and `hint_title` of `Transit` now
  always have the columns `_en` and `_ru` of the migrations of the package. In a language
  without a column they are read and written in its base language or the fallback language
  (`name_column()` in `bazis.contrib.statusy.models_abstract`).

Found by the evals of bazis-cli.

## Upgrading a project that hit the bug

If `makemigrations` of the project wrote a migration into the installed package and it was
applied, the database lacks the `_ru` columns. The upgrade removes the file of that
migration, its record stays:
`SELECT name FROM django_migrations WHERE app = 'statusy' AND name > '0006_transits_related_through';`
returns it. Then add the columns back and forget that migration:

```sql
ALTER TABLE statusy_status ADD COLUMN IF NOT EXISTS name_ru varchar(255) NOT NULL DEFAULT '';
ALTER TABLE statusy_transit ADD COLUMN IF NOT EXISTS name_ru varchar(255) NOT NULL DEFAULT '';
ALTER TABLE statusy_transit ADD COLUMN IF NOT EXISTS hint_title_ru varchar(255) NULL;
DELETE FROM django_migrations WHERE app = 'statusy' AND name > '0006_transits_related_through';
```
