# bazis-statusy 2.15.0

Requires bazis 2.16 and bazis-permit 2.11 (unchanged). No migration.

## Fixes

- **The schemas of the body of the transit endpoint have the same names on every Python and
  on every start.** The body of a transit without a payload was named after
  `dict | None`: `Union_body_type` on Python 3.14, `DictOrNone_body_type` on 3.12 and 3.13.
  It is `DictOrNone_body_type` everywhere. The body of a transit with a payload was named
  after the ids of its payload models (`PayloadType_3478...016_body_type`, new on every
  start); it is named after the models now (`PayloadType_<model>_<model>_body_type`, the
  names sorted), and the fields of the payload (and its `required`) follow the models in
  that order. The OpenAPI and the `state_actions` of the same code are identical across
  Python versions and runs, as the contract check of bazis-front (`bazis_front contract
  --check`) requires.

## Changes

- **`Model.get_transit_payload_type(transit)`: the payload type of a transit from the model
  class**, without an object (the creation of an object computes its default status in the
  database). It is the one implementation: `item.transit_payload_type(transit)`, which the
  transit endpoint and `state_actions` call, returns it. A model that changes the payload
  type of a transit overrides the classmethod; an override of `transit_payload_type` is not
  seen by the code that asks the class (the contract export). Calling the instance method
  with the class in place of an object (`Model.transit_payload_type(Model, transit)`, as
  bazis-front 0.6 does) keeps working.
- **`GET /{item_id}/status_history/` of `StatusyRouteSetBase`**: the history of the transits
  of the item, the oldest first, as `{"data": [...]}`; each record has the `transit`
  (`id`, `name`), `status_src`, `status_dst`, `dt`, the `author` (a resource identifier
  `{id, type}`, null for a transit of the system) and the `payload` of the transit (null
  without one). It is an action of bazis-permit with the new operation
  `StatusyAccessAction.HISTORY` (`shop.order.item.history.<selector>.<status>`), kind
  `other` in `x-bazis`: the item must be visible (404 as at its retrieve) and the user must
  have the `history` permission (403). A route set that must not give it leaves
  `action_status_history` out of its `actions`. The calculated field `status_history`
  (2.12) stays for the clients that read the history together with the item.
- **The payload of a transit is stored.** `transit_apply` (and so the transit endpoint)
  writes the validated payload, `model_dump(mode='json', by_alias=True)` of the payload
  type, to `extra['payload']` of the history record, which the actions receive. A transit
  without a payload type, and the records made before this version, have no payload.

## Upgrading

- **The history records now keep the payloads of the transits**, and whoever has the
  `history` permission reads them through `status_history`. Review the payload models of
  the transits: a field that carries a secret or personal data that must not be kept is
  marked `Field(exclude=True)`. Sent as a dict (the transit endpoint) it is validated and
  given to the actions, but not stored; a payload model instance passed to `transit_apply`
  loses such a field before the validation, so pass a dict there.
- **Roles get no history until the permission is granted**: grant
  `<app>.<model>.item.history.<selector>.<status>` to the roles that may read the
  payloads and the statuses, which the field permissions of the item may hide (`view` is
  not enough).
- `create_statusy_transit(transit, author, extra=None)` takes the `extra` of the history
  record: an override of the method must accept it and pass it on.
